## User Scenarios & Testing *(mandatory)*

### User Story 1 - 제목만으로 빠르게 등록 (Priority: P1)

사용자로서, 떠오른 할 일을 제목만 입력해 즉시 등록할 수 있다. 그래서 아이디어가 떠오르는 즉시
기록하여 잊어버리지 않는다. (docs/REQUIREMENTS.md US-001)

**Why this priority**: 이 앱의 핵심 가치는 "빠른 기록"이다. 제목 하나만으로 등록이 끝나지 않으면
할 일 관리 도구로서의 존재 이유가 사라진다.

**Independent Test**: 제목만 채운 채 등록을 요청하면, 다른 값 입력 없이도 Backlog 맨 위에 카드가
생기는지 확인하는 것만으로 완전히 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 제목만 입력한 상태, **When** 등록을 요청하면, **Then** 우선순위는 자동으로
   보통(MEDIUM)으로 설정되고 Backlog 칼럼 맨 위에 새 항목이 나타난다.
2. **Given** 같은 칼럼(Backlog)에 이미 항목이 있는 상태, **When** 새 항목을 등록하면, **Then** 새
   항목이 기존 항목보다 항상 더 위에 놓인다.

---

### User Story 2 - 상세 정보를 포함해 등록 (Priority: P2)

사용자로서, 할 일에 설명·우선순위·시작예정일·종료예정일을 함께 설정할 수 있다. 그래서 할 일의
중요도와 기한을 명확히 관리할 수 있다. (docs/REQUIREMENTS.md US-002)

**Why this priority**: 빠른 기록(P1) 다음으로 중요한 가치는 "관리 가능한 기록"이다. 제목만으로는
나중에 우선순위를 판단할 근거가 없다.

**Independent Test**: 설명·우선순위·시작예정일·종료예정일을 모두 채워 등록한 뒤, 응답과 화면에
입력한 값이 그대로 반영되는지 확인하는 것만으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 사용자가 설명, 우선순위(높음), 시작예정일, 종료예정일을 모두 입력한 상태, **When**
   등록을 요청하면, **Then** 입력한 값이 모두 그대로 저장·반환된다.
2. **Given** 종료예정일 입력란, **When** 지나간 날짜를 선택하면, **Then** 등록이 거부되고 사유가
   표시된다.

---

### User Story 3 - 잘못된 입력으로부터 데이터 보호 (Priority: P3)

사용자로서, 실수로 잘못된 값을 입력해도 시스템이 이를 막아줘서 보드가 이상한 데이터로
어지럽혀지지 않기를 기대한다.

**Why this priority**: 핵심 등록 흐름(P1, P2)이 갖춰진 뒤에 다듬어도 무방한, 방어적 품질
요구사항이다.

**Independent Test**: 제목 누락/공백/길이초과, 설명 길이초과, 잘못된 우선순위 값 등 각각을
개별적으로 제출해보고 매번 저장 없이 거부되는지 확인하는 것만으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 제목을 비워둔 상태, **When** 등록을 요청하면, **Then** "제목을 입력해주세요"라는
   사유와 함께 거부되고 아무것도 저장되지 않는다.
2. **Given** 제목이 200자를 초과한 상태, **When** 등록을 요청하면, **Then** 사유와 함께 거부된다.
3. **Given** 우선순위로 목록에 없는 값(예: "URGENT")을 지정한 상태, **When** 등록을 요청하면,
   **Then** 사유와 함께 거부된다.

---

### Edge Cases

- 제목이 공백 문자로만 채워진 경우 → 실제 내용이 없는 것으로 간주해 거부한다.
- 제목이 정확히 200자인 경우 → 허용, 201자부터 거부한다 (경계값).
- 설명을 입력하지 않은 경우 → 빈 값이 아니라 "설명 없음" 상태로 취급한다.
- 종료예정일이 오늘 날짜와 같은 경우 → 허용한다(등록 가능). `docs/API_SPEC.md`의 "오늘 이후"라는
  문구는 이 동작과 어긋나므로 별도로 문구를 "오늘부터"로 정정할 필요가 있다 (Next Actions 참고).
- 두 건의 등록 요청이 동시에 들어와 같은 위치(맨 위)를 계산하는 경우 → 이 스펙 범위 밖(별도 이슈).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 제목만으로(다른 값 없이) 새 할 일을 등록할 수 있어야 한다.
- **FR-002**: 시스템은 우선순위를 지정하지 않으면 보통(MEDIUM)을 기본값으로 적용해야 한다.
- **FR-003**: 사용자는 등록 시 설명, 우선순위(낮음/보통/높음), 시작예정일, 종료예정일을 선택적으로
  함께 입력할 수 있어야 한다.
- **FR-004**: 시스템은 지나간 날짜가 종료예정일로 입력되면 등록을 거부하고 사유를 알려야 한다.
- **FR-005**: 시스템은 제목이 비어있거나 공백만 있으면 등록을 거부하고 "제목을 입력해주세요"라는
  사유를 알려야 한다.
- **FR-006**: 시스템은 제목 200자 초과, 설명 1000자 초과, 목록에 없는 우선순위 값 각각에 대해
  등록을 거부하고 원인을 구분할 수 있는 사유를 알려야 한다.
- **FR-007**: 시스템은 새로 등록된 항목을 항상 Backlog 칼럼의 맨 위에 놓아야 한다 (다른 칼럼에
  놓이거나 중간에 삽입되지 않는다).
- **FR-008**: 시스템은 등록 시점에 "시작일"과 "완료일"을 사용자가 지정하지 못하게 해야 한다 —
  이 값들은 항상 비어 있는 채로 생성되고 이후 시스템이 자동으로 채운다.
- **FR-009**: 시스템은 등록이 성공하면 방금 만들어진 항목의 전체 정보(부여된 식별자와 위치 포함)를
  즉시 돌려줘야 한다.
- **FR-010**: 시스템은 거부된 모든 등록 요청에 대해 일관된 형식의 사유를 제공해, 입력 문제와 시스템
  장애를 구분할 수 있게 해야 한다.

> 위 FR 번호는 이 파일 내부에서만 쓰이는 로컬 번호이며, `docs/PRD.md`의 전역 FR-001~FR-008
> 번호 체계와는 다른 별개의 네임스페이스다. 이 스펙 전체는 docs/의 FR-001(티켓 생성)에 대응한다.

### Key Entities *(include if feature involves data)*

- **티켓(Ticket)**: 칸반 보드를 구성하는 작업 단위. 제목, 설명, 소속 칼럼(생성 시 항상
  Backlog), 우선순위, 칼럼 내 위치(정렬 순서), 시작예정일/종료예정일(사용자 입력),
  시작일/완료일(시스템 전용, 생성 시점엔 항상 비어 있음), 생성/수정 시각을 갖는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 제목만 입력해 별도 설정 화면을 거치지 않고 바로 새 할 일을 등록할 수 있다.
- **SC-002**: 잘못된 입력(빈 제목, 지나간 종료예정일, 목록에 없는 우선순위 등)은 100% 그 자리에서
  구체적인 사유와 함께 거부되며, 어떤 경우에도 보드에 저장되지 않는다.
- **SC-003**: 새로 등록된 할 일은 예외 없이 Backlog 칼럼의 맨 위에서 발견된다.
- **SC-004**: 등록 직후 사용자는 자신이 입력한 값(설명·우선순위·예정일 포함)이 누락이나 변형 없이
  그대로 반영된 결과를 확인할 수 있다.

## Assumptions

- 이 기능은 인증/권한 개념이 없는 단일 사용자 MVP를 전제로 한다 (docs/API_SPEC.md 명시).
- "시작일"과 "완료일"은 이 기능의 범위가 아니다 — 다른 기능(FR-005, FR-007)이 이후에 채운다.
- 동시 등록 시 위치(순서) 계산 경합 조건은 이 스펙에서 다루지 않는다.
